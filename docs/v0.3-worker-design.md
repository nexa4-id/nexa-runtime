# Nexa v0.3 Native Worker Integration Design

## Goals

Expose the existing native worker pool to Nexa programs without changing the meaning of existing v0.2 programs.

Target source form:

```rust
fn main() {
    let base = 21;
    let task = worker.submit {
        base * 2
    };
    let result = worker.wait(task);
    print(result);
}
```

Expected output: `42`.

## Proposed semantics

- `worker.submit { expression }` schedules one integer expression and returns an opaque task handle.
- Local integer variables referenced inside the block are captured by value at submission time.
- Task handles are not copyable and may be consumed by `worker.wait` only once.
- A task handle cannot be captured by another worker block.
- `worker.wait(handle)` blocks until completion and evaluates to the integer result.
- Worker panic, channel disconnection, invalid handle, duplicate wait, and arithmetic failure become explicit runtime errors.
- A program with no worker expressions executes without creating a worker pool.
- The pool is shut down and joined when VM execution exits, including error exits.

## Compiler and bytecode changes

The lexer needs tokens for the worker namespace, member access, submit, and wait. The parser should recognize submit blocks as expressions and wait calls as expressions.

The compiler should emit a separate worker expression program for each submit block, together with a capture descriptor mapping outer local slots to worker-local slots. It should reject unknown identifiers, nested task captures, duplicate declarations, and attempts to use a task handle as an integer expression.

A suggested bytecode shape is:

- `Submit { worker_code, captures }`: snapshot captured integer locals, enqueue the worker closure, and push a task handle.
- `Wait`: consume a task handle and push its integer result.

The compiler must track local value kinds (`I64` and `Task`) independently from the runtime stack. A task variable is single-use and must not silently coerce to an integer.

## Runtime representation

Use a VM value enum rather than storing all locals as `i64`:

- `I64(i64)`
- `Task(TaskHandle)`

The task handle should wrap an owned result receiver and an internal identifier. Moving the value out of a local slot enforces single consumption. Waiting on an empty or already-consumed slot reports an invalid/reused handle error.

The worker closure should execute a small integer VM over captured values and return `Result<i64, RuntimeError>`. Catch panics at the worker boundary and translate them into a stable panic error. Do not expose panic payloads or internal channel errors as language-level API.

## Worker engine review items

The v0.2 pool is a useful base. Before integrating it, address or explicitly document:
- thread spawn failure should be returned as an error rather than panic;
- queue mutex poisoning should not cascade into panics in all workers;
- panic and ordinary task errors should be distinguishable to the waiter;
- task submission racing with shutdown needs a defined result, not an assertion panic;
- low-priority starvation should be documented or bounded by a fairness policy.

Do not add lock-free queues or a new dependency unless measurements demonstrate a need.

## CLI

Preserve `nexa run <file.nx>`. Add an optional `--workers N` argument to `run`; validate that N is positive. The worker pool should be lazily initialized only when the program contains a submit operation.

## Required tests

- Basic submit/wait returns 42.
- Captures are snapshots of local values.
- Two or more tasks complete and return independent values.
- A non-worker v0.2 program still runs.
- Compile-time rejection of unknown captures, invalid task use, and duplicate declarations.
- Runtime reporting for panic, arithmetic error, invalid handle, and repeated wait.
- Pool shutdown drains accepted tasks and rejects submissions after shutdown.
- CLI accepts a worker count and rejects malformed/zero counts.

## Implementation gate

This document is a design proposal, not a claim that the language feature is implemented. The current execution environment has no Rust toolchain, so compiler/runtime changes must be validated in a Rust-enabled environment before they are represented as complete.
